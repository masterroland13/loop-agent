# Hal Agent 演进路线图

> 来源：  
> 1）行业调研（为何推 Agent Window、痛点与趋势）  
> 2）CLI → Agent Window 演进分析  
> 3）企业 AI「Demo→生产」机制论  
> 4）产品愿景：全流程项目交付（阶段规划表 + Skills + Harness）  
> 5）竞品原语：Pi Agent、DeepSeek Harness（DSH）→ **§3**  
> 6）运行时纠偏讨论（2026-08）：**Loop + 死抱目标** → **§0（脊柱，优先于一切阶段口号）**  
>
> 适用：本仓库自建 Hal Agent（React + FastAPI + LiteLLM）  
> **统一思想（纠偏脊柱）：**  
> `Agent 的基础 = 观察 → 决策 → 行动 → 把结果变成下一次观察；且每一次观察都对照同一个目标，决定继续 / 换手段 / 向人求助 / 收工。`  
> **产品原则：** 可监督轨迹 → 可靠工具环 → 死抱目标 → 记忆压缩 →（其后才）Task / Project OS / 多 Agent  
> **北极星：** 有多少**对照目标完成的闭环**真正进入日常工作流且可运营（而非「聊得爽」或「环在空转」）  
> **长期定位：** 以阶段门禁 + Skill/Harness 驱动的项目交付工作台（Project OS）；Project OS = **目标在项目时间尺度上的死抱**，不是另一条与 Runtime 无关的产品线

## 0. 统一思想：Loop + 死抱目标（纠偏脊柱）

> 本节是路线图的**裁判标准**。后面 MVP / v1 / v2 / §12 若与本节冲突，**以本节为准做纠偏**，再改阶段表述。  
> 思想会继续进化；进化时先改 §0，再级联改阶段表——避免「阶段口号漂移、Runtime 仍漂」。

### 0.1 定义（一句话拆开）


| 词 | 含义 | 在 Hal 里落在哪 |
| -- | ---- | -------------- |
| **目标（Goal）** | 本轮/本任务「怎样算做完」；可被人改，但改了必须留痕 | Turn Goal / 任务验收 / 阶段出口产物 |
| **观察（Observe）** | 模型下一拍能用的事实：工具结果、审批结果、人的 Steer、压缩后的摘要 | `working[]` 里的 tool/user 消息；将来的事件流 |
| **决策（Decide）** | 对照目标：继续 / 换手段 / 向人求助 / 收工 | `chat_complete`；应被检查点与 Goal 约束，而非自由闲聊 |
| **行动（Act）** | 调工具或等人审批；写盘必须经门 | `propose_*`、只读工具、MCP |
| **回灌（Loop）** | 行动结果变成下一次观察，进入下一拍 | `run_agent_loop` 的 `working.append` + 再调用 |


**环在转 ≠ Agent 在干活。** 空转的典型：多次 `ls`/`cat`、三轮用户「好的」无回复、触顶中止、一次 Reject 后整任务蒸发。

### 0.2 每一拍的合法出口（死抱目标的控制信号）

每一拍结束，只允许四选一（可组合表述，语义必须清晰）：

1. **继续** — 同一目标下再观察/再行动（信息仍不足，但路径清楚）  
2. **换手段** — 同一目标，换工具或参数（如 `python` → `python3` / venv）  
3. **向人求助** — 需要审批、澄清、或 Steer；人的输入是**新的观察**，不是任务取消（除非人明确 Stop）  
4. **收工** — 目标已满足，或目标被证明不可达并给出阻塞原因 + 已得事实  

**禁止的第五态：** 沉默、只刷工具轨迹、或「友好结束语」但目标未对照。

### 0.3 机械环 vs 质量环（现状判断）

Hal **已经具备机械环**（`run_agent_loop`：tool → append → 再 `chat_complete`）。缺口在**质量**：


| 环节 | 机械现状 | 质量缺口 | 用户可感事故 |
| ---- | -------- | -------- | ------------ |
| 目标 | 埋在首条 user 里 | 无显式 Turn Goal；「好的」冲淡意图 | 同意查配置后变成逛目录 |
| 观察 | 原始 shell/JSON 回灌 | 吵、长、低密度；失败未结构化 | token 膨胀、继续乱探 |
| 决策 | 模型自由选工具 | 无「相对目标还差什么」检查点 | 探索爆炸、轮次烧光 |
| 行动 | 审批门强 | 环境默认弱（如裸 `python`） | 假失败、差最后一公里 |
| 停止 | 轮次上限 / gate 模板 / 模型自觉 | 停止≠目标达成；失败易早 `done` | 空白轮、模板一句了事 |
| 可见 | SSE + 部分 audit | 中间态不落库；audit 常无 `session_id` | 以为 Agent 死了 |

**纠偏结论：** 下一阶段主线不是「再堆 UI / 再堆 Project OS 阶段」，而是把机械环做成**对照目标的质量环**；UI 与 Project OS 只是把 Goal / 观察 / 求助画出来。

### 0.4 「能用」的最低标准（Foundation 验收）

同时满足才算离开「Demo 壳 + 偶发能跑」：

1. 用户给出目标后，系统有**显式 Goal**（可展示、可注入每拍）  
2. 多轮工具后，每次决策能回答：相对 Goal，进度 / 阻塞是什么  
3. **成功**：有产物或可核验结论；**失败**：有阻塞原因 + 已得事实 + 可选下一步求助——不是沉默  
4. 人 Reject / 命令失败 → 作为观察**续环**（换手段或求助），默认不掐死任务  
5. 轮次触顶 → **软着陆总结**（对照 Goal），不是只报错消失  
6. 过程可监督：关键观察与审批进轨迹；用户能看见环在推进  

### 0.5 与上层概念的嵌套（一张图）

```text
                    死抱目标（控制信号）
                           │
     ┌─────────────────────┼─────────────────────┐
     ▼                     ▼                     ▼
 Turn Goal            Task 验收              阶段出口产物
 (单轮/单任务)         (v2 任务卡)            (Project OS)
     │                     │                     │
     └──────────► 同一次 Observe→Decide→Act→Observe 环 ◄──────────┘
                           │
              人的审批 / Steer = 环内观察
              轨迹事件流 = 观察可回放
              Preset = 收窄行动面，减少偏离目标
```

- **Pi Steering / DSH Trajectory / Preset**（§3）= 强化环的「看得见、改得了、收得住面」  
- **Task UI / Project OS**（§7 / §12）= Goal 在更长周期上的形态；**不能替代** §0 的环  
- **多 Agent**（v3+）= 多个环；单环不稳时引入只放大不可观测  

### 0.6 思想进化时怎么改路线图

1. 先改 **§0**（定义 / 合法出口 / 能用标准）  
2. 再改 **Foundation / v1 必须做**（是否仍服务质量环）  
3. 最后改 v2+ / §12 文案（避免愿景句先行、Runtime 空洞）  
4. 竞品新功能默认进「观察」；唯有强化 §0.2 四出口或 §0.4 标准才进 backlog（与 §3.5 纪律一致）

## 2. 从 CLI 到 Agent Window（启示摘要）

**判断：** Window 更好解决了看见/点选/留存；**没有自动解决**可靠环、目标、权限、成本；还削弱了 CLI 可组合性。

**对路线图的直接启示（服从 §0）：**

1. **保留 CLI 之魂**：同一 Runtime；Window = 监督 UI，CLI/CI 同 API  
2. **窗口优先补环的短板**：Goal 可见、步骤时间线、diff/shell 审批、失败续环  
3. **显式投喂** = 高质量观察：`@file`、diff、命令输出为一等公民  
4. **人在环内**：审批与 Steer 是观察，不是只当断路器  
5. **进化顺序：** 先让环对照目标收工（Foundation）→ 再 Task/阶段表 → 最后多 Agent  

（CLI 痛点对照表详见历史版本讨论；此处不重复展开，以免压过 §0。）

## 3. 企业 AI：Demo → 生产（机制论摘要）

最大瓶颈常是机制而非单点模型。本仓库产品化映射：


| 步骤 | 本仓库落地 | 与 §0 的关系 |
| ---- | ---------- | ------------ |
| 盘点 | 资产/健康/会话 | 观察系统自身 |
| 选场景 | 窄闭环（记忆门 / 读改审批 / **目标闭环**） | 先选可死抱的目标 |
| 建系统 | 审批门、audit、规则版本 | 行动可拦、观察可回放 |
| 纳资产 | Skill 晋升、Owner | 复用成功手段 |
| 统底座 | LiteLLM、工作区 | 行动面统一 |
| 扩流程 | 使用率/拒绝率/一次通过率 | 用数据看环是否在完成目标 |


**离开 Demo 的最小定义：** 有明确业务/任务闭环 + 审批 + 审计 + Owner/状态 + 运行指标 + 统一模型入口——且闭环用 §0.4 衡量，而不是「能聊」。

## 4. Pi Agent 与 DeepSeek Harness 借鉴（原 §0.3）

> **术语：** §12 **Harness** = 阶段门禁；DSH harness = runtime 外壳。借原语不借框架宗教。  
> **用 §0 重读竞品：** Trajectory = 观察可回放；Steer = 人中途注入观察；Preset = 收窄行动面减少偏离目标；Fork = 从某次观察重来仍带着 Goal。

### 4.1 对照与决策


| 能力 | Hal | 决策 | 服务 §0 的哪一拍 |
| ---- | --- | ---- | ---------------- |
| Diff/Shell/Memory 门 + hunk | ✅ 差异化 | **保持做深** | 行动可拦；人→观察 |
| 事件流 / 轨迹真源 | ◐ | **P0 必借（DSH）** | 观察可回放 |
| Steering | ❌ | **P0 必借（Pi）** | 求助/纠偏不掐环 |
| Preset 档位 | ◐ 零散 toggle | **P1 借档位** | 决策面干净 |
| 会话 Fork | ❌ | 事件流之后 | 换手段/重来 |
| `/compact` + 保留指令 | ◐ | 增量 | 观察变瘦 |
| 只读批处理（阉割 Code mode） | ❌ | P3；写禁止进批 | 降空转成本 |
| Cordis / 换皮 / Creator 改 runtime | — | **明确不做** | 不服务用户闭环 |


**监督闭环一句话（与 §0 对齐）：**

```text
看得见（轨迹）→ 拦得住（审批）→ 改得了方向（Steer）→ 对照目标收工（Goal）→ 收得住面（Preset）
```

### 4.2 必做 / 应做（杠杆序）


| 优先级 | 项 | 为什么（问题→用处） | 落点 |
| ---- | -- | ------------------- | ---- |
| **P0** | 事件流真源 + 时间线 | 聊天可见 ≠ 能复原模型所见；无此则 fork/审计悬空 | 扩展 audit/会话事件；前端时间线 |
| **P0** | Steering | 人只能等/停 = 断路器；中途纠偏才是监督台 | loop 工具间隙读 pending；写入事件流 |
| **P0\*** | **Goal + 检查点 + 失败续环** | 环空转、目标漂移、Reject 掐死任务（§0 / §5） | Foundation；\*与竞品并列为本仓脊柱 |
| **P1** | Preset 档位 | 全工具面导致闲聊也带写、易误提案 | 2–3 档过滤 tools |
| **P2** | Fork / 手动 compact | 探索回退、上下文救命 | 依赖事件流 |
| **P3** | 只读批处理、配置导出、权限姿态文案 | 降成本/复现 | 不挡 P0 |


### 4.3 明确不做（近期）

整迁 Cordis；用 DSH/Pi 替换 Hal；Creator 改 runtime；Code mode 批写；SYSTEM.md 整段替换默认系统提示；为热点绑死单模型；单环未稳上子 Agent；削弱审批门；每工具开关墙当主 UX；把 §12 Harness 改造成 DSH runtime。

### 4.4 已吸收、不必再当「对标立项」

AGENTS.md 分层、Skills 渐进披露、三类审批 + hunk、`audit_events` 雏形、turn_meta、LiteLLM 入口、工具轮次可配 + 触顶软着陆、Shell/Diff 审批区折叠。

## 7. Foundation — 质量环 + 死抱目标（当前主线）

**目标：** 满足 §0.4；消灭「环空转 / 空白轮 / 一次失败即放弃」。

**实施跟踪（Living）：** [`docs/foundation-status.md`](foundation-status.md) — 进度、占比、backlog、§0.4 验收。  
**方案与三档定义（Stable）：** [`docs/foundation-f4-f6-plan.md`](foundation-f4-f6-plan.md) — F4/F6 定义、中间路线、已拍板决策。

### 7.1 必须做


| # | 能力 | 为什么（要解决的问题） | 有什么用 | 验收 |
| - | ---- | ---------------------- | -------- | ---- |
| F1 | **显式 Turn Goal** | 意图被「好的」冲淡，模型丢目标 | 每拍注入同一 Goal；UI 可展示 | 深挖类任务不再无目标漫游 |
| F2 | **进度检查点** | 局部最优（再 ls 一次） | 每 N 工具或 gate 回来强制对照 Goal | 更早收工或求助，少烧轮次 |
| F3 | **失败续环（修订）** | 超时/失败无限续或 Reject 后仍纠缠 | Reject/部分应用 → 本轮结束；超时/失败 → hint 续环至多 1 次，再失败则告知用户 | Reject 即停；环境失败有一次自救，不空转 |
| F4 | **观察结构化/截断** | 原始输出噪音大、易炸上下文 | 回灌短事实，而非整页 ls | 同任务 token↓、乱探↓ |
| F5 | **行动环境默认可用** | 裸 `python` 等假失败 | cwd/venv/`python3` 默认正确 | 同类脚本一次跑通 |
| F6 | **中间态落库可见** | 工具在转、聊天像没回 | 用户信任；可调试 | 不再出现多轮「好的」无 assistant |

| F9 | Foundation 狗粮剧本 | 固定：「解释报错→同意深挖→产出结论」；断言有 Goal 对照结论 |

### 7.4 Foundation 成功标准

## 14. 风险与约束（工程纪律）

1. **不静默写盘**；审批是环内观察，不是可关的装饰  
2. **不假装已实现**  
3. **成本可见**：循环有预算与早停；触顶对照 Goal 总结  
4. **密钥不进提示词**  
5. **先单环做稳**：多 Agent 在 v3+  
6. **不丢 CLI 之魂**  
7. **机制产品化**：Owner、生命周期、审计进系统  
8. **全流程防空心**：阶段必须有出口产物  
9. **愿景与节奏分离**：Project OS 服从 §0；先 Foundation→v1  
10. **竞品借鉴纪律**：见 §4.3；不削弱审批、不整迁内核  
11. **死抱目标纪律：** 无 Goal 不启长环；无对照不收工；禁止空转当进度

## 16. 一句话路线

> **先把工具环做成对照目标的质量环（Foundation）→ 收尾治理与诚实（MVP）→ 轨迹 + Steer + Preset 让人开得动环（v1）→ 把 Goal 升级成 Task / 阶段出口（v2 / Project OS）→ 最后多环并联（v3+）。**

综合定位：

- 相对大厂 Window：拼 **对照目标收工** + 可监督  
- 相对 CLI：补齐看见/可拦/可记，保留可组合  
- 相对 Demo 困局：机制产品化 + 闭环进工作流  
- 相对 Pi/DSH：借轨迹、Steer、Preset；脊柱是自家 §0，不是换皮  
- 相对 Project OS：阶段门禁是 **项目级死抱目标**，建在同一 Runtime 之上  

**Hal Agent 不是又一个 Chat，而是：让 AI 在可监督的环里死抱目标把事做完，并逐步长成项目交付的运行与治理层。**

## 17. 愿景：项目全流程操作系统（Project OS）

> 地位：**愿景层**；**依赖 §0 质量环 + v1 监督台**。  
> 含义：按阶段推进；时间+内容规划表可改留痕；大项绑 Skill + Harness；出口产物门禁。  
> **用 §0 重读：** 阶段 Done = 项目时间尺度上的「收工」；缺产物进入下阶段 = 非法收工。

### 17.1 要防的三种跑偏


| 风险 | 约束 |
| ---- | ---- |
| 项目管理套壳 | 每阶段必须有可执行产物 + Agent 动作 |
| Skills 只写不用 | Skill 可调用；Harness 绑出口 |
| 一次做全平台 | 先单项目 + 三阶段 |


### 17.2 阶段模型（摘要）

`initiate` → `research` → `design` → `build` → `trial` → `accept` → `close`  
（可选 `spike` / `release`）  
每阶段：目的、难点、**出口产物**；无出口则 Harness L1 提醒 / L2 需确认 / L3 硬阻断。

### 17.3 规划表与 Skill / Harness

- 工作项含：目的、难点、计划/基线时间、状态、出口产物、skill_ids、harness_id、变更日志  
- **计划可改；改动进审计**  
- Agent 日常上下文 = 当前项目 + 阶段 + 工作项 + 对应 Skill  
- Skill = 做法包；Harness = 门禁/白名单/校验（≠ DSH runtime）

### 17.4 与能力路线嵌套


| Project OS 层 | 依赖 |
| ------------- | ---- |
| 项目/阶段/规划表 | v2 Task 超集；Foundation Goal 语义 |
| Skill | v1 注入 + 资产库 |
| Harness | MVP/v1 审批审计 + v2 验收 |
| 开发阶段真干活 | Foundation 质量环 + v1 工具/diff |
| 全阶段多项目 | v3+ |


**推荐切片：** 项目+三阶段表 → 每阶段 1 Skill + 轻 Harness → 开发接 tool/diff → 验收对照立项成功标准 → 再模板化。  
**狗粮：** 用本仓库真实小需求走立项→开发→验收。

### 17.5 开放问题

阶段是否强制统一？项目与会话一对多？Skill 是否首期仅本地？L3 是否对个人过严？  
实现前短评审改本节即可，**无需推翻 §0–§11**；若与 §0 冲突，改本节。
